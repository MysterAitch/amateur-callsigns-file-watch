Why keying off the raw bytes recovers what the tidy file loses

Each distinct raw token this entity was published under, shown with its bytes and the normalises_to edges the ledger derived from it (raw → cleaned → entity, each carrying its named rule). Where two tokens differ only in invisible characters — a trailing space, a non-breaking space — the current normalised CSV shows both as the same clean form, so you can no longer tell which one carried the extra characters. The ledger keeps the raw token, the rule and the attributes together, so nothing is quietly lost.

Every observation is real. The entity view shows them all, with provenance — it never silently picks a winner. That is the join key obeying transparency-first.

The full background for one callsign

What the ledger asserts for the resolved entity. Where a published form differs from its canonical form, or a derived observation applies, a record fidelity note appears — each computed from the claims themselves, with a "show the working" disclosure and a link to examine the source. A clean, unremarkable record shows no such note. The notes are things we note or observe in the published data; where a value looks inconsistent with the rules we derive, we flag the discrepancy and draw no conclusion about why. A derived observation is produced from the query result today; cross-source links (FOI correspondence, ITU home-country resolution) are a later sub-stage and are noted, not shown.

What this view does not yet show

Stage 3a proves one real page serving live data end-to-end (raw bytes → claims → SQLite → in-browser query). Deliberately out of scope here, and arriving in later sub-stages:

  • the both-engines playground (SQLite beside DuckDB/Parquet) and hand-written SQL;
  • the vocabulary and normalisation demonstrations (licence-type census, the cleaning catalogue, the regional-renderings walk-through);
  • licence class and dates in the timeline — the snapshots name these under different columns with different value vocabularies and date formats, so the timeline tracks register status only until that cross-schema normalisation is done;
  • cross-source links — FOI correspondence and ITU home-country resolution — which are not yet available in the claim ledger;
  • the offline (PWA) opt-in download of the claim-ledger database.
Scope: this folds the register-snapshot publications the archive holds — not Ofcom's other disclosures (FOI correspondence, forbidden-suffix lists, statistics). A callsign absent here may still appear in those, and the register never listed every un-issued callsign, so absence is never proof of availability.
