Trial your own queries against the claim ledger

The Ledger page folds one callsign into a dossier. This page hands you the whole surface: write your own read-only SQL and run it, in your browser, over the same raw-keyed claim-ledger database. It is where a query gets trialled before it is promoted to a future curated “explorations” section — start from an example, or write your own.

Read-only · queried in your browser from the raw-keyed claim-ledger database (issue #361) over range requests — the database is never downloaded whole; your browser fetches only the pages each query needs. Only SELECT and WITH queries run; results are capped at 500 rows. Register snapshots only; other Ofcom disclosures are not folded in yet.

Run a query

Only SELECT and WITH queries are accepted — anything else is refused before it runs. Results are capped at 500 rows. Point-lookups on the indexed columns (entity, cleaned, raw_subject) are fast; a whole-corpus scan over range requests is honestly slow, so prefer an indexed filter or your own LIMIT.

what you are querying

Schema

The database keeps the ledger compactly — provenance split onto an observation row, low-cardinality strings dictionary-encoded, and the derived layer reconstructed by a view rather than stored. You query the flat claims view; the base tables are there when you want them.

The claims view — the flat contract

Columns of the flat claims view
columnmeaning
layerraw (as Ofcom published it) or derived (a normalisation the ledger computed)
raw_subjectthe token exactly as published — kept verbatim, whitespace and all (indexed)
cleanedthe human-readable canonical callsign; the direct-lookup key (indexed)
entitythe RSL-less placeholder key every regional rendering collapses to (indexed)
predicatewhat is asserted: @listed, a Status/Type column name, or normalises_to
objectthe asserted value (e.g. a status of Allocated)
rulethe named rule behind a derived edge (e.g. the cleaned-callsign rule); NULL for raw claims
source_file · ordinal · vintageprovenance: which archived file, which row, and the snapshot date

Base tables

Base tables the claims view is reconstructed from
tablewhat it holds
observationone published register row — its raw_subject, resolved cleaned/entity, and source (the indexes live here)
attrthe real attribute claims against an observation, predicate/object dictionary-encoded
sourceone row per archived snapshot: its source_file and vintage
predicate · objectthe small dictionaries the attr rows reference
ph_overridethe rare observation whose placeholder edge diverges from its resolved entity
Every derived normalises_to edge and every @listed anchor in the claims view is reconstructed by the view from the observation, not stored — so the flat contract is exactly what the ledger asserts, at a fraction of the size.
planned · not built

A richer DuckDB-WASM lane is planned

This console is the SQLite lane: point-lookups and modest folds over range requests. A heavier DuckDB-WASM lane — analytical and graph folds over the Parquet tier — is planned as an opt-in alongside it, for the whole-corpus aggregates that are slow here. It is not built yet; this note marks the intent so the SQLite lane is not mistaken for the whole story.
