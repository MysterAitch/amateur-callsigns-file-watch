Data status

A build-time-derived tracker of every dataset this mirror holds or knows exists, and how far each has been carried through the processing pipeline — the work-queue and the gap-finder in one. Nothing here is hand-maintained: every row and cell is computed on each deploy from the committed archive, each entry's meta.json, and the source register, so it cannot drift from reality.

one of three axes

This is axis 1 of three — the processing view? (definition of the processing-progress axis in the glossary)

The mirror describes its data along three separate questions, deliberately not conflated. This page tracks the first — how far each file has been carried through the pipeline — shown as an operational ladder, like build tasks:

1Read → 2Understood → 3Validated → 4Normalised → 5Enriched

The other two are kept apart from it:

  1. Source authority? (definition of the source-authority axis in the glossary) — how official the origin is (Official → FOI → Reference → Community → Self), from each entry's meta.json. Shown here only as the small “Source” tag on each row, for orientation.
  2. Claim confidence? (definition of the claim-confidence axis in the glossary) — how much to trust a given fact (As-published → Computed → Looked-up → Community → Best-guess), the tiered claim layer surfaced on the Ledger.

A high-authority source can still yield a low-confidence claim, which is why the three are kept apart. All three axes, with every rung defined, live in the glossary.

Per-type rollup

Known but not yet held

Datasets the source register names that the processed archive does not yet hold. These sit at “Read ✗” on the grid: known to exist, provenance recorded, not yet fetched or converted. This is the standing work-queue.

coverage over time

Series coverage & gaps

Datasets grouped into series over time, so coverage, staleness and gaps are visible. A long silence between consecutive held vintages is flagged with a plain next-step — no action is automated; the gap is surfaced and the option named.
